# Mutation inventory and implementation contracts

Step 1 deliverable. Source baseline: working tree inspected on 2026-10-29. This document specifies future behavior; none of the proposed command APIs exists as a result of this step. See [summary.md](summary.md) and [progress.md](progress.md).

## Reading the inventory

Source paths below are relative to the repository root. Function names are the source anchors; proposed command names are design names under `bg2e_composer::command`, grouped into `scene`, `component`, `material`, `geometry` and `lighting`.

Each row inherits these rules unless overridden:

- Origin is explicit local editor intent; imported service requests use `PreparedImport`. Targets are captured at dispatch, never obtained again from current selection. Identity includes document generation and retained node/component/drawable/material identity, plus submesh index and topology revision where applicable. Identifiers alone do not authorize rebinding to a replacement object.
- Authored edits use `Always`, support undo, affect the document, and are atomic. Optional selection uses `UserPreference`, default off, and has no document impact. Exclusions use `Never`.
- `CPU` means the existing `enqueueCpuValueUpdate` boundary; `GPU` means the conservative `enqueueRendererUpdate` boundary. `Retained` requires the existing resource-version retirement contract. All execute/undo/redo/adoption and completion operations are serialized on the owner thread before frame acquisition. Unknown/custom resource behavior uses GPU.
- `Edit` invalidation means cancel stale bake sources, mark document state only on effective success, invalidate renderer temporal histories, refresh active camera/environment as needed and request a frame. `Graph` additionally synchronizes tools and selection references. `Material` also restores both live draw material and serializable material definition. Replay uses the same invalidation, without dispatching another command.
- Multi-target actions capture a deduplicated target list and execute as one atomic composite. No-op targets contribute no entry; one failed child restores all applied children.

## Reusable core contract for step 2

Proposed public types live directly in `bg2e::app`: `Command`, `CommandQueue`, `CommandHistory`, `CommandTransaction`, `CompositeCommand`, `CommandResult`, policy/context and completion types. The core depends on neither Composer nor scene, draw/render, GPU, reflection or UI. The application supplies execution, compatibility, preference and safe-release adapters. Names remain provisional until actual headers exist.

### Identity, metadata and policy

A command exposes a stable action/category key, display name, undo capability, `Never`/`Always`/`UserPreference`, document impact (`None` or `Document`), and estimated retained bytes. Origin context distinguishes editor, prepared import/result, navigation, runtime and history replay. The dispatcher validates permitted origins; generic setters do not infer origin. Replay is an internal operation, not an opportunity to submit a fresh command.

Resolve before accepting execution or beginning a transaction, in this order:

1. Navigation/runtime/replay cannot record, regardless of preferences. Reject an attempt to submit a recording-required command from these origins; do not silently downgrade it.
2. `Never` disables recording, `Always` requires it, and only `UserPreference` invokes the application's category resolver. Unknown/unresolved categories are rejected rather than guessed.
3. Effective recording requires undo support. Reject invalid combinations before mutation. Nonrecorded document edits require an explicit compatibility disposition and nonhistorical dirty notification.
4. Freeze the resolved policy, origin, target identity and document generation for the entire queued action/transaction. Preference changes affect future dispatch only.

Composer authored categories default to `Always`; selection is configurable, default off. A prepared import/result records only through its authorized publication command, never directly from a worker. Existing selection entries remain undoable after selection history is disabled; do not filter the cursor or rewrite old policies. New unrecorded selection changes preserve the branch, and undoing an older selection entry can intentionally replace the current selection.

### Execution, results and ownership

Lifecycle: `Pending -> Executing -> Applied`; undo moves `Applied -> Executing -> Undone`, redo moves back through `Executing`. Cancellation/stale rejection/no-op moves pending work to `Discarded`. Failed mutation with successful recovery returns to its prior stable state with a failure result; failed recovery enters `Faulted`. Branch pruning/eviction transitions retained entries to `Discarded` and schedules safe release.

Queue admission is not application success. The queue owns pending command instances and frozen context. An executor hook schedules the head at the caller's safe boundary; only one operation is in flight and later operations cannot overtake it even across different graphics queues. The execution owner holds the instance through completion; successful recorded execution transfers it to history. Nonrecorded/no-op/rejected work goes to the release adapter. Completion fires exactly once after recovery/recording, with `Applied`, `NoOp`, `Rejected`, `Cancelled`, `Failed` or `Faulted` and diagnostic information. Stale document/renderer generation invokes cancellation completion; queue shutdown also settles pending completions. Callback failure must not change an already committed operation's result or cursor.

`execute`, `undo` and `redo` must report effectiveness and recovery outcome. NoOp means no affected state changed, not merely that a target vanished. Invalid targets are rejected. Recovered failure, rejection, cancellation and no-op leave state tokens, cursor and redo intact. Reserve history capacity, entry metadata, resource accounting and recovery storage before mutation; do not publish successfully and then discover recording cannot allocate. Stage fallible invalidation/resource preparation inside the recoverable operation. Notifications after commit cannot be responsible for model correctness.

Commands prepare before publication, retain before state, and restore partial mutations on failure, including serializable definitions, graph placement and active references. A composite executes children in order and undoes them in reverse order; on execute/redo failure it undoes completed children, and on undo failure it reapplies already undone children in forward execution order. The failing child must recover its own partial work. Any failed compensation faults the history, blocks execute/adopt/undo/redo and cancels dependent pending work. Preserve diagnostics and retained recovery objects. Recovery requires explicit document reload/replacement or application repair followed by a new baseline; clearing an error flag is insufficient.

`adoptApplied` accepts an already-applied command only from its active transaction/prepared integration token, with captured before/after and validated generation. It does not call execute. Recording storage and budget must be reserved before preview mutation. Adoption failure restores preview state; arbitrary post-mutation notifications cannot safely use this API.

### Transactions

Initially one transaction per history. Begin at the safe boundary captures before state once, resolves policy and reserves history/rollback resources. Updates carry the same transaction ID, target/property identity and origin. Commit waits for prior updates, captures final state and adopts one entry; unchanged final state discards the preview and preserves redo. Cancel restores before state and records nothing. Focus loss/escape, target/document replacement and shutdown must explicitly settle or cancel it; save commits a valid preview before writing, and blocks if settlement fails.

Only consecutive absolute updates with the same transaction ID/target/property can coalesce. Never coalesce incremental edits or cross command/commit/cancel boundaries. Other model edits/replay wait until the transaction settles; runtime evaluation follows the conflict rule below. Text entry, sliders, color editors and gizmos need explicit activation/change/deactivation/cancel signals through optional SDK adapters; no debounce-only grouping.

### History identity, compatibility and dirty state

Allocate monotonic, never-reused document state IDs, distinct from cursor/index and document generation. Every effective recorded document edit stores before/after IDs. Selection-only entries carry the same document ID on both sides. Undo/redo restore those IDs; branching creates a fresh ID. Saving stores `(generation, documentStateID, nonhistoricalRevision)` only after complete successful publication. Dirty compares that tuple and an active transaction's effective document preview against the saved tuple. Selection previews never dirty the document.

Track persisted nonhistorical navigation/runtime changes with a separate monotonic revision; undo cannot erase it. Do not count navigation as a command. A failed save leaves saved identity and path metadata unchanged. `sourcePath`/`savePath` are IO metadata outside commands. Eviction retains saved identity for comparison even if unreachable; never infer clean from index zero, depth or cursor reuse. If saved state was evicted or pruned, only reaching its exact token or successfully saving clears dirty.

Each unrecorded action declares one of: `Preserve` (proven disjoint or compatible), `InvalidateRedo` (retain applied undo only when safe), or `ResetHistory` (replacement/destructive incompatible change). The conservative default for unknown external authored mutations is reset, new baseline ID and nonhistorical dirty revision. Failed/no-op actions do not invalidate. Unrecorded document edits conflicting with applied entries reset history, rather than leaving unsafe undo. Runtime transient evaluation and selection preserve redo. Navigation preserves redo because property commands restore captured absolute authored values against the same identity; it can change the visible result between replays. Destroying/replacing a target outside reversible commands resets affected document history before releasing it; never replay against an object found by reused name/identifier. Recorded structural replacement retains old identities and is reversible in normal history order.

### Memory and resource release

Bound both entry count and retained bytes across undo, redo, transactions and pending recording reservations. Account command-local data once; shared retained resource tickets keyed by resource/version identity account shared payload once while any command holds it. Include detached branches, images, CPU geometry and estimated GPU payload; estimates are conservative, not a promise of exact driver allocation size. Growing transactions reserve additional budget before each update. Reject a command larger than the configured limit before applying it; never silently execute without undo. Evict oldest applied entries only at stable boundaries, preserving current token and reachable chain. New effective recorded edits discard redo only after success. The application may expose explicit limit changes, never an implicit loss of reversibility.

Discard/eviction hands resource owners to the application's release adapter at its safe boundary. Core code performs no GPU waits or device cleanup. History references are not proof that a resource remains usable: `StageScene::releaseRetired` currently calls `cleanupTree` even when a node is retained elsewhere. Structural integration must prevent this cleanup while history owns the branch, then retire resources after extraction/submissions release them. Undo reattachment must reuse usable retained instances, not cleaned shells.

## SDK, ownership and runtime integration decisions

- `Node` currently offers append/remove and `orderedComponents`, without indexed insertion contracts. Step 5 needs a narrow placement-preserving API/adapter for siblings and equal-priority components; re-adding at the end is not restoration. Preserve priorities, owner pointers, scene registration and active environment/camera selections.
- `prepareTools` deduplicates shared drawable/CPU mesh ownership by cloning. Stabilize this before command identity capture; deduplicate material targets by actual owner and binding, and explicitly choose all shared users when intentionally modifying a shared resource. Attribute snapshots must deep-copy mutable settings; sharing immutable image resources is acceptable. No global TextureCache changes: its device-specific weak realizations remain unchanged.
- Retain detached components/subtrees without serialization, including plugin-provided components. Retain module leases with any component, reflection getter/setter/action callback, factory product or command implementation. There is no demonstrated Composer history/module lease integration yet: step 5 must add an explicit adapter or prevent module unload while retained work exists. Without an undo adapter for a custom reflected action, reject that edit in Composer; ordinary SDK users retain their existing direct operation path.
- Generated lightmap directories are currently staged in `applyLightmapBake`; its catch removes them only before material mutation, and no successful-publication source lease is evident there. Introduce shared source-lifetime ownership for live bindings and retained command versions; do not delete a source on undo, branch pruning or bake-context cancellation while another owner needs save/redo. Keep source leases through successful save publication or final safe release. Retain images/settings/texture bindings alongside paths. Keep engine/device alive until command resources are safely released; cancel producers, settle queue/transactions and release history before engine teardown.
- Optional SDK intent handlers must expose typed property/action/texture targets and explicit interaction boundaries before mutation, while preserving immediate/default behavior without handlers. `DrawMaterialEditor::onChanged` is post-mutation (also on partial failure); `ReflectionWidget::EditHandler` transports opaque operations; `ComponentInspector` already has optional add/remove/draw callbacks. Extend these seams rather than making SDK setters or notifications history-aware. UV2 publication requires the same optional preparation/adoption seam.
- Choose authored-base versus evaluated-runtime semantics: commands restore authored/base values; animation/controllers remain independent and never create entries. While editing a property written by an active controller, pause that writer for the captured interaction, without replacing its instance, and resume its previous state afterward. A runtime controller may immediately overwrite the visible evaluated result after commit/undo; history promises authored-state restoration, not a permanent visible pose. If a component cannot separate authored values or pause its writer safely, reject the conflicting editor interaction until it supplies an adapter. Untracked persisted writes use the explicit nonhistorical/reset policy above. Navigation remains available outside those conflicting interactions.
- Graphics Settings is a real scene-edit route despite `setExcludeSceneSettingsFromAutomaticPersistence(true)`. Step 4/6/8 must route its light/environment bindings through Composer's dispatcher, including imported settings batches; application-only render settings stay outside history. This extends the source baseline without migrating rendering APIs.

## Step 3 implementation checkpoint

Implemented source paths now include `CommandDispatch.cpp`, `command/Dispatcher.*` and `command/scene/NodeCommands.*` in Composer. Actual first command names are `bg2e_composer::command::scene::RenameNode` and `SetNodeEnabled`. Rename uses the CPU-value queue; enabled state and replay use the conservative queue. The scheduler adapter also exposes the retained-resource boundary. Category registrations reject conflicting synchronization choices. Current commands retain CPU values and weak scene identities only; adding native-resource mementos requires the renderer/retirement adapter in later resource steps.

`Document::commands` owns its dispatcher/history. `dirty` remains a synchronized UI-facing cache of stable history state and nonhistorical revisions. `StageScene::save` rejects pending/active/faulted history and calls `markSaved` after successful scene/resource publication, leaving source/save paths outside mementos. Open/new prepare a fresh generation/dispatcher before publication and keep the old document/history until scene reattachment succeeds. Recovery restores stage order, active references and selection; failed recovery reports an explicit external history fault. Faulted scene rendering/input stop, while discard/replacement and teardown remain possible.

`applyCommandEffects` centralizes renderer/bake/tool/selection/frame effects without recursively recording. The dispatcher envelope compensates its model edit if those effects fail, then faults history if restoration fails. Enabled commands retain before/after active camera/environment/fill/known-environment state and preserve controller instances. `refreshCamera(true)` avoids controller cloning for this command path; a later interaction adapter must still pause conflicting runtime writers as specified above.
